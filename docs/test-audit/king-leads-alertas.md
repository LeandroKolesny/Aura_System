## Funcionalidades identificadas

### `pages/king/KingLeads.tsx` (`/king/leads`) — "CRM Comercial"
1. Kanban de 6 colunas (`new → contacted → demo → negotiation → won/lost`) sobre `leads` do `AppContext`, carregado via `loadLeads()` (que, para `role === OWNER`, chama `kingApi.leads()` → `GET /api/king/leads`, que na verdade lista **empresas** com `plan=FREE`/`subscriptionStatus=TRIAL`/`salesStatus` preenchido — não existe uma entidade "Lead" própria do King, o pipeline é construído em cima do model `Company`).
2. Ao montar, chama `loadLeads()` e `kingApi.markLeadsSeen()` (`PATCH /api/king/leads/mark-seen`) para zerar o badge de "novos leads" usado pelo `KingLayout`/`KingDashboard` (auditado pelo Agente 1).
3. Cards de estatística: Total de Leads, Leads Ganhos, Valor Potencial (soma de `value`), MRR Conquistado (soma de `value` dos `won`).
4. Ações por lead: avançar/voltar no funil (`handleMove`), menu de ações (marcar Ganho/Perdido, reabrir), modais dedicados para mover para `demo` (data/observações), `lost` (motivo + comentário) e `won` (escolha de plano de conversão), e um link direto de WhatsApp (`buildWhatsAppUrl`) com mensagem pré-formatada.
5. "Novo Lead": modal que chama `addLead()` do `AppContext`.
6. RBAC: a tela não faz nenhuma checagem de papel própria — depende inteiramente do guard de rota do `KingLayout` (Agente 1) no frontend e de `requireOwner` nas duas rotas backend do escopo (confirmado abaixo). Não há ação sem guarda correspondente no backend.

### `pages/king/KingAlerts.tsx` (`/king/alerts`) — "Alertas do Sistema"
1. Lista o "Histórico de Alertas" a partir de `systemAlerts` do `AppContext`, com estatísticas (Total, Ativos, Inativos, Globais) e badge por tipo (`info`/`warning`/`error`/`success`).
2. Cria um novo alerta (`addSystemAlert`) com título, mensagem, tipo e destinatário (`all` ou uma empresa específica, escolhida entre `companies` do `AppContext`).
3. Alterna o status ativo/inativo de um alerta (`toggleSystemAlertStatus`) — não há "excluir" alerta, só desativar (soft toggle).
4. **A rota de backend real usada não é `/api/king/*`** — é `aura-backend/src/app/api/system-alerts/route.ts` (`GET`/`POST`/`PATCH /api/system-alerts`, via `services/api.ts` → `systemAlertsApi`). Confirmado por grep em `services/api.ts`/`AppContext.tsx`: não existe (e nunca existiu) um endpoint `/api/king/alerts`. Essa rota é compartilhada: o mesmo `GET` alimenta tanto o histórico do King (`KingAlerts.tsx`) quanto o banner de avisos exibido às clínicas (`pages/SystemAlerts.tsx`, `pages/Dashboard.tsx`) — todas fora do escopo desta tarefa, mas dependem do mesmo código agora corrigido.
5. RBAC: `POST`/`PATCH` de `/api/system-alerts` já checavam `role === "OWNER"` corretamente (confirmado, não é bug). `GET` é aberto a qualquer usuário autenticado — correto, pois clínicas precisam ver os alertas endereçados a elas.

## Vazamento de dados sensíveis (mesmo padrão do Agente 2) — verificado, SEM bug

- `GET /api/king/leads`: `prisma.company.findMany` é chamado sem `select` no nível raiz (`include: { users: {...} }` apenas para o admin), mas a rota **constrói manualmente** o array `leads` no retorno (`companies.map(c => ({ id, clinicName, contactName, ... }))`), listando explicitamente cada campo exposto — nenhum campo do model `Company` que não está nessa lista (ex.: `asaasCustomerId`, `businessHours`, `cnpj`) chega ao JSON de resposta, mesmo a query interna trazendo a linha inteira do Prisma. Diferente do bug do Agente 2 (`queryPatients`/`queryAppointments`/`queryCompanies`), aqui não há um `NextResponse.json(companiesCruas)` — o mapeamento explícito já protege o vazamento. **Não corrigido porque não há nada para corrigir**, mas caso este endpoint alguma vez passe a repassar o objeto do Prisma direto, o mesmo risco do Agente 2 se aplicaria.
- `GET /api/system-alerts`: `prisma.systemAlert.findMany` também sem `select`, mas o model `SystemAlert` só tem `id, title, message, type, target, status, createdAt` — nenhum campo sensível existe no modelo. Sem risco.

## Problemas encontrados durante a revisão

1. **[CORRIGIDO — erro de API não comunicado, `if` sem `else`] `KingLeads.tsx`, `handleAddLead`: a chamada a `addLead(...)` não era `await`ada e o resultado nunca era checado — o modal fechava e o formulário era limpo incondicionalmente, mesmo que a criação do lead falhasse no backend.**
   Evidência (código original, linhas 91-103): `addLead({...}); setNewLead({...}); setIsModalOpen(false);` sem `await`, sem checar `result.success`, sem `showAlert`. Mesmo padrão de bug já identificado como o mais comum nas sessões anteriores (resultado de mutação assíncrona ignorado).
   **Consequência prática mais grave**: `addLead()` sempre chama `leadsApi.create()` → `POST /api/leads`, que exige `user.companyId` (`aura-backend/src/app/api/leads/route.ts`, linha 86-88: `if (!user.companyId) return 403 "Usuário sem empresa"`). Um usuário `OWNER` normalmente **não tem** `companyId` (é dono da plataforma, não de uma clínica — ver fixtures `MOCK_OWNER = { companyId: null }` usadas nos próprios testes de `king-leads.test.ts`), então o botão "Novo Lead" deste CRM **sempre falhava** silenciosamente em produção para uma conta OWNER real. Isso é uma incompatibilidade de arquitetura mais profunda (o pipeline de leads do King é modelado em cima de `Company` existente com `salesStatus`, não existe uma rota de criação de lead "do zero" em `/api/king/leads` — só `GET`/`PATCH`), e corrigi-la de verdade exigiria uma rota nova + possivelmente um novo campo/entidade para representar um prospect que ainda não é uma empresa cadastrada. Isso está **fora do escopo de correção de bug** desta tarefa (seria uma feature nova, com migração de schema). O que foi corrigido aqui é a parte que É um bug direto e sem ambiguidade: a falha agora é **comunicada ao usuário** via `showAlert`, em vez de fingir sucesso.
   **Correção aplicada**: `handleAddLead` agora é `async`, aguarda `addLead(...)`, e só limpa o formulário/fecha o modal quando `result.success` é `true`; caso contrário exibe `showAlert(result.error ?? 'Erro de sistema. Tente novamente.', { variant: 'danger' })` e mantém o modal aberto.
   **Recomendação para sessão futura**: decidir o desenho correto para "adicionar um prospect manualmente" no CRM do King (nova rota `POST /api/king/leads` + como representá-lo sem um `Company` real) — ver seção "Testes recomendados".
2. **[CORRIGIDO — estado local desatualizado + chamadas de API redundantes] `KingLeads.tsx`, `handleConfirmDemo`/`handleConfirmLost`: cada uma fazia DUAS chamadas PATCH separadas para a mesma rota (`kingApi.updateLead` direto, com os campos extras, seguido de `moveLead(id, status)`, que dispara um SEGUNDO `kingApi.updateLead` só com `{status}`). A segunda chamada sobrescrevia `salesMovedAt` sem necessidade, e o `setLeads` local de `moveLead` só mesclava `{ ...l, status }` — os campos `demoAt`/`demoNotes`/`lostReason`/`lostComment` enviados na primeira chamada nunca eram refletidos no estado local (`leads`) do `AppContext`.**
   Evidência (código original): `handleConfirmDemo` chamava `kingApi.updateLead(companyId, {status:'demo', demoAt, demoNotes})` e, na sequência, `moveLead(lead.id, 'demo')` (que internamente faz **outro** `kingApi.updateLead(id, {status})`); `context/AppContext.tsx`, `moveLead`: `setLeads(prev => prev.map(l => l.id === id ? { ...l, status } : l))` — só `status` é mesclado.
   **Consequência prática**: depois de confirmar uma demo ou registrar uma perda, o card do Kanban não mostrava a data/observação da demo nem o motivo/comentário da perda até a página ser recarregada (o `loadLeads()` só roda uma vez por sessão, controlado por `loadedRef`) — o dado ficava correto no banco (a primeira chamada persistia certo), mas a UI ficava visivelmente desatualizada e havia o dobro de chamadas de rede necessárias, dobrando a superfície de falha parcial (uma das duas chamadas podia falhar e deixar backend/estado local inconsistentes entre si).
   **Correção aplicada**: `context/AppContext.tsx`, `moveLead(id, status, extra?)` agora aceita um 3º parâmetro opcional (`demoAt`/`demoNotes`/`lostReason`/`lostComment`), faz **uma única** chamada `kingApi.updateLead(id, { status, ...extra })` e mescla `{ ...l, status, ...extra }` no estado local. `KingLeads.tsx` (`handleConfirmDemo`/`handleConfirmLost`) agora chama só `moveLead(id, status, {...})`, eliminando a chamada duplicada e a inconsistência de estado. O fluxo de conversão (`won`), que também chama `companiesApi.update()` para ativar o plano, foi mantido como estava — esse `companiesApi.update()` é quem sincroniza a lista `companies` do contexto (não é redundante).
3. **[CORRIGIDO — feature quebrada por não carregar dados, mesma classe de regressão já documentada no código para `tickets`] `AppContext.tsx`: `systemAlerts` nunca era populado a partir do backend — não existia (em lugar nenhum do arquivo) uma chamada a `systemAlertsApi.list()`. O array só recebia itens localmente, via `addSystemAlert`, dentro da mesma sessão do navegador.**
   Evidência: `grep systemAlertsApi` em `context/AppContext.tsx` só retorna usos de `.create` e `.toggleStatus`; o próprio arquivo já documenta esse exato padrão de bug, já corrigido para outro recurso: `// REGRESSÃO: ticketsApi.list() nunca era chamado em lugar nenhum...` (linha ~2079, função `loadTickets`). `KingAlerts.tsx` também não tinha nenhum `useEffect` — a tela nunca pedia os dados.
   **Consequência prática**: o "Histórico de Alertas" do King ficava **sempre vazio** logo após um `F5`/nova sessão, mesmo com alertas ativos no banco — e o mesmo vale para o consumo desse mesmo estado em `pages/SystemAlerts.tsx` e no banner de avisos de `pages/Dashboard.tsx` (fora do escopo de arquivos desta tarefa, mas corrigidos de graça pela mesma correção, por compartilharem o estado `systemAlerts`/`AppContext`).
   **Correção aplicada**: nova função `loadSystemAlerts(forceReload?)` em `AppContext.tsx` (mesmo padrão de `loadTickets`/`loadLeads`, com `loadingRef`/`loadedRef`), chamando `systemAlertsApi.list(false)` (todos os alertas, ativos e inativos — o filtro de "só ativos" já é feito no próprio backend quando necessário) e populando `systemAlerts`. `KingAlerts.tsx` agora chama `loadSystemAlerts()` num `useEffect` de montagem.
4. **[CORRIGIDO — bug de visibilidade de dados] `GET /api/system-alerts`: quando o requisitante é `OWNER`, o filtro `where: { OR: [{target:'all'}, {target: user.companyId}] }` usava `user.companyId`, que para o OWNER é sempre `null` — então o próprio criador de um alerta direcionado a UMA clínica específica (`target = companyId`) nunca conseguia vê-lo de volta no seu próprio "Histórico de Alertas" (só via os alertas `target:'all'`).**
   Evidência: `aura-backend/src/lib/auth.ts` (`AuthUser.companyId: string | null`) confirma que `OWNER` não tem empresa; `aura-backend/src/app/api/system-alerts/route.ts` (`GET`, código original) montava o `where` da mesma forma para qualquer papel.
   **Correção aplicada**: quando `user.role === "OWNER"`, o `GET` agora ignora o filtro por `target` (`where = {}`, mais o filtro de `status` quando `activeOnly=true`) — o OWNER vê o histórico completo de tudo que ele mesmo enviou, global ou direcionado. O comportamento para clínicas (`ADMIN`/demais papéis) não mudou.
5. **[CORRIGIDO — falta de validação Zod, regra obrigatória do `CLAUDE.md`] `aura-backend/src/app/api/system-alerts/route.ts` (POST/PATCH) e `aura-backend/src/app/api/king/leads/route.ts` (PATCH) não validavam o corpo da requisição com Zod — apenas checagens manuais (`if (!title || !message)`), e o `where` do `GET` de `system-alerts` era tipado como `any` (outra regra do `CLAUDE.md`: "sem `any` no TypeScript").**
   Consequência prática (baixa severidade, já que ambas as rotas exigem `OWNER`, um papel confiável — mas ainda uma violação de defesa em profundidade): um `type`/`status` inválido em `system-alerts` ou um `status`/`plan` fora do enum em `king/leads` chegava direto no Prisma, que rejeitaria em runtime com uma exceção genérica capturada pelo `catch` → 500 "Erro interno" — funcional, mas sem uma mensagem 400 clara indicando qual campo é inválido.
   **Correção aplicada**: schemas Zod adicionados nas três rotas (`createAlertSchema`/`updateAlertSchema` em `system-alerts`, `patchLeadSchema` em `king/leads`), com transformação de caixa (`'warning' → 'WARNING'`) mantendo compatibilidade com o que o frontend já envia; `where` do `GET` de `system-alerts` agora tipado como `Prisma.SystemAlertWhereInput`.

## Problemas encontrados durante a revisão (verificados e considerados corretos — não é bug)

- **`kingGuard.ts` (`requireOwner`)**: reutilizado sem alterações, conforme instrução — já auditado a fundo pelo Agente 1.
- **Nenhum vazamento de campo sensível** nas duas rotas do escopo (`/api/king/leads`, `/api/system-alerts`) — ver seção dedicada acima.
- **RBAC de `POST`/`PATCH /api/system-alerts` já estava correto** (`role !== "OWNER" → 403`), assim como `requireOwner` em ambas as rotas de `/api/king/leads*`.
- **`companiesApi.update()` sendo chamado tanto no fluxo de conversão (`won`) quanto no de perda (`lost`) em `KingLeads.tsx`, além do próprio `PATCH /api/king/leads` também setar `plan`/`subscriptionStatus` automaticamente para esses dois status**: não é um bug — são dois mecanismos com propósitos diferentes. O `companiesApi.update()` no frontend é quem mantém a lista `companies` do `AppContext` sincronizada (usada por outras telas do King, fora deste escopo); o auto-ajuste do backend em `PATCH /api/king/leads` só dispara de fato quando o `status` muda via `moveLead` sem que o frontend já tenha enviado `plan` (hoje isso só aconteceria em um caminho que o frontend atual não usa) — mantido como estava, sem remover nenhum dos dois, para não regredir a sincronização da lista de empresas.
